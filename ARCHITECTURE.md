# Architecture

The scaffold is built: the workspace, the xtask, the firmware on the C6 and the S3, the LoRa radio, the report task, one stub per source, and CI. The report task sends the test bytes `[node_id, 0xAA, 0x55]` every `heartbeat`.

Not built yet: the real sources (each stub only logs `not ported yet`), the packet format, the send policy, deep sleep and `lp-tempsense`, HA devices, `cargo xtask schemas` and the decoder. What this file says about them is the target design. Their validation rules arrive together with them. Build them to match, and update this file wherever the real code ends up different. [Next steps](#next-steps) gives the order.

## Concepts

Three things are kept separate, so they can be combined freely:

- **Source:** one thing a node reads: `ds18b20`, `battery`, `eder`, `pyromat`. Each source has a kind number and schema in `crates/proto`, a parser crate where needed, and one firmware module.
- **Node:** one ESP32 with one radio, identified by `node_id`. It runs one or more sources and sends one packet that holds the complete dataset of all of them.
- **HA device:** a grouping that exists only on the receiver side. By default each node is one device. `nodes.toml` can split a node's sources across several devices, or collect sources from several nodes into one device.

The legacy projects become source sets: temp-station = `battery` + `ds18b20` in deep sleep, eder gateway = `eder`, pyromat gateway = `pyromat`.

## Repo layout

There is one Cargo workspace, split by *source*, not by device. esp-hal and a per-board module absorb the chip differences, so the sources don't depend on any particular chip.

```
crates/            host-testable no_std libraries, no esp-hal dependency
  proto/           LoRa packet format, schema registry (single source of truth for decoders)
  policy/          send policy (thresholds, min_interval, heartbeat); also runs on the coprocessor
  eder/            Eder MultiControl UART telegram parser
  pyromat/         Köb Pyromat CAN frame -> field mapping
  onewire/         1-Wire + DS18B20 (ROM search, CRC8, scratchpad) over a minimal bus trait
  lp-shared/       #[repr(C)] HP<->LP shared-memory layout (ROM table, last sent values, time since last send, flags)
firmware/
  node/            HP-core firmware: src/main.rs, src/config.rs, src/report.rs, src/sources/<source>.rs, src/board/, src/radio.rs + src/radio/<sx126x|sx127x>.rs
  lp-tempsense/    DS18B20 poller for C6 LP core / S3 ULP-RISC-V (esp-lp-hal)
xtask/             build orchestration, config validation, schema export
decoder/           receiver side: Node-RED decode function (later: Home Assistant integration)
boards.toml        hardware: board name -> chip, radio chip, pin numbers
nodes.toml         deployments: node name -> board, node_id, power mode, sources + their parameters; optional HA devices
schemas.json       generated by `cargo xtask schemas`; never edit by hand
.github/           CI workflow
.vscode/           rust-analyzer settings for the firmware
```

## Design rules

- **Logic goes in `crates/`, glue goes in `firmware/`.** Parsing, encoding, send decisions and protocol state machines are pure code with host unit tests. CI has no hardware-in-the-loop testing, so host tests are the only automated check. Keep firmware tasks thin enough that they hold nothing worth testing.
- **Pins and the radio chip are configuration, not code.**
  - **`boards.toml`:** each board entry gives the chip, the radio chip (`sx127x` | `sx126x`), the SX126x TCXO voltage if there is a TCXO, and the pin numbers for LoRa SPI/RST/IRQ/BUSY, 1-Wire buses, UART, TWAI, battery ADC and the optional OLED.
  - **Validation:** the xtask checks the pins against the chip and rejects:
    - pins that don't exist
    - flash pins (S3 modules with octal PSRAM also lose GPIO 33–37, but that isn't checked: the feather-s3 and t3s3 use them for LoRa)
    - pins assigned twice
    - a `busy` pin missing on an `sx126x` board, or set on an `sx127x` board
    - an `irq` pin missing on an `sx126x` board (`sx127x` boards may leave it out, see [Radio](#radio))
    - `tcxo_mv` on an `sx127x` board, or with a voltage lora-phy can't set (it can set 1600, 1700, 1800, 2200, 2400, 2700, 3000 and 3300)
    - 1-Wire pins that aren't LP/RTC-capable when the coprocessor polls them

    It warns on strapping pins.
  - **Hand-off to firmware:** the xtask exports the pins (`AIO_PIN_LORA_SCK`, …) and `tcxo_mv` (`AIO_TCXO_MV`) as env vars and selects cargo features. The chip feature (`esp32c6` | `esp32s3`) is forwarded to esp-hal, esp-rtos and the other esp crates. The radio feature (`sx127x` | `sx126x`) picks the radio family's file in `src/radio/`, and with it the lora-phy radio type.
  - **The only pin-handling code:** firmware has one board module, `src/board/`. `board::init(peripherals) -> Board` starts esp-rtos and is the only code that turns pin numbers into esp-hal pins (with `AnyPin::steal`, which is safe because the xtask rejects pins used twice). It gives the sources ready-made drivers. Sources never see pin numbers. Code that differs between the chips goes into `src/board/<chip>.rs`; so far nothing does, so these files don't exist yet.
  - **Hardware changes:** rewiring a board or adding one is an edit to `boards.toml`, not to Rust code. A device's pins are decided right before it gets flashed; until then a board entry may hold placeholders.
- **A node's firmware is composed from sources.** There is one binary, `firmware/node`.
  - Each source is a module `src/sources/<source>.rs` behind a cargo feature (`source-eder`, …). The xtask turns the node's `sources` in `nodes.toml` into these features, and `sources::spawn_all` in `src/sources/mod.rs` spawns the task of each one.
  - Each source runs as an Embassy task (esp-rtos executor). It writes its latest snapshot, a struct from `crates/proto`, into a shared `embassy-sync` cell and signals the report task.
  - The report task (`src/report.rs`) owns the radio: it starts it, applies the send policy to the node's whole dataset, encodes the sections and transmits. `main` only calls `board::init`, spawns the tasks and returns.
  - This replaces the legacy `ServiceManager` and service classes. Don't recreate the singleton.
- **Each node has a power mode,** `power = "always-on" | "deep-sleep"`.
  - Sources that listen continuously (`eder`, `pyromat`) need `always-on`. Each source's entry in `crates/proto` states this.
  - Pollable sources (`ds18b20`, `battery`) work in both modes.
  - In `deep-sleep` mode, the node wakes, samples each source once, sends if the send policy says so, and sleeps again.
  - With `ds18b20` on a deep-sleep node, the coprocessor polls the sensors and runs the send policy on their readings, so the HP core only wakes to send. The HP core samples its own sources (`battery`) whenever it wakes.
  - The HP core also arms a backup timer of 2 × `heartbeat` before each deep sleep, in case the coprocessor hangs. A backup wake restarts the coprocessor and sends.
  - The last sent values and the time since the last send are kept in RTC RAM in the `lp-shared` layout, where the coprocessor compares against them. On the C6 that needs care; see [Targets](#targets).
- **Per-deployment values come from `nodes.toml`, never from code.** That covers node ID, power mode, sources, send intervals, change thresholds (overriding the schema defaults), calibration factors and HA device grouping. The xtask exports the selected node's entry as env vars, and the firmware reads them with `env!` into consts. Node IDs must be unique.
- **The xtask also validates each node.** It rejects:
  - a `board` that isn't in `boards.toml`
  - a source name it doesn't know, or a parameter the source doesn't take
  - a source whose pins the board doesn't define
  - a listening source on a deep-sleep node
  - more than one repeated-group source per node (see [Packet](#packet))
  - a worst-case packet over 255 bytes; for `ds18b20` the worst case is the board's 1-Wire buses × `max_per_bus`
  - a device entry that names a missing `node.source`, or a source listed in more than one device
  - a `node_id` listed in `reserved_node_ids`, the first bytes that legacy nodes still send (see [Decoding & Home Assistant](#decoding--home-assistant))

  It prints the worst-case airtime and the duty cycle at `min_interval`, and warns above 1 %.
- **`crates/onewire`, `crates/lp-shared` and `crates/policy` must also compile for the LP core.** That means no alloc, no `core::fmt`, no floats and small code. LP SRAM on the C6 is about 16 KB, and the legacy S3 ULP reserved 4 KB.
- Avoid the heap by default and use `heapless` collections. Only add `esp-alloc` when there is a concrete need.
- Deep sleep, the LP core, ADC, RMT, TWAI and RTC RAM may sit behind esp-hal's `unstable` feature. Their APIs can break on esp-hal minor version bumps, so pin the esp-* versions in the workspace `Cargo.toml`.

### Adding a source

1. Write a parser crate in `crates/` if needed.
2. Add a kind to `crates/proto` with its schema (including default thresholds), its power requirement and golden-byte tests.
3. Add `firmware/node/src/sources/<source>.rs` behind a `source-<source>` feature.
4. Add its pins to `boards.toml` if it needs any.

No decoder change and no new binary are needed. Any node can then list the source, and any HA device can include it.

## Node configuration

`nodes.toml` names each node, its sources and, optionally, HA devices. The nodes and devices below are examples, not real deployments, but `reserved_node_ids` holds the real legacy values.

```toml
# First bytes that legacy nodes still send: feather-s3 0x00, pyromat 0x01, t3s3 0x02,
# eder gateway 0x7C (first byte of its MAC). Remove each once its node is reflashed.
reserved_node_ids = [0x00, 0x01, 0x02, 0x7C]

[nodes.heizraum]
board = "feather-s3"
node_id = 4
power = "always-on"
heartbeat = 600                                         # s
min_interval = 30                                       # s
sources.eder = {}                                       # per-field thresholds go here
sources.ds18b20 = { max_per_bus = 3, threshold = 2 }    # threshold in raw 1/16 °C

[nodes.garten]
board = "feather-s3"
node_id = 7
power = "deep-sleep"
heartbeat = 1800
min_interval = 60
sources.battery = {}
sources.ds18b20 = { max_per_bus = 3, poll = 60, threshold = 2 }

# Optional. Sources not listed in any device stay in their node's default device.
[devices.eder]
name = "Eder MultiControl"
sources = ["heizraum.eder"]

[devices.heizung_temps]
name = "Heizung Temperaturen"
sources = ["heizraum.ds18b20", "garten.ds18b20"]        # may span nodes
```

## Targets

Only the C6 and the S3 are supported (no H2).

| | C6 | S3 |
|---|---|---|
| Role | new nodes | all existing deployments (pyromat and eder gateways, temp stations) |
| HP target | `riscv32imac-unknown-none-elf` | `xtensa-esp32s3-none-elf` (`+esp` toolchain, build-std) |
| Low-power coprocessor | LP core, `riscv32imac-unknown-none-elf`, LP GPIO 0–7 only | ULP-RISC-V, `riscv32imc-unknown-none-elf`, RTC GPIO 0–21 |
| TWAI (CAN) | 2 | 1 |

S3 stays fully supported for now. Still, keep S3-only code inside `board/`, `#[cfg(feature = "esp32s3")]` blocks, the xtask's toolchain switch (`Chip::cargo`) and the spots marked "S3 only" in `firmware/node/build.rs`, `firmware/node/.cargo/config.toml` and `.github/workflows/ci.yml`, so it can be dropped later just by deleting it.

The `ds18b20` source polls from the HP core on always-on nodes. On deep-sleep nodes, `lp-tempsense` polls on the coprocessor, which can only drive 1-Wire on LP/RTC-capable pins. The xtask's `boards.toml` validation enforces this.

Between polls the coprocessor must halt and be restarted by its own timer; a coprocessor that keeps running draws far more than deep sleep. As of esp-hal in October 2026:

- **S3:** supported. `UlpCoreWakeupSource::Timer` restarts the ULP, and esp-lp-hal's `ulp_riscv_halt()` really stops it.
- **C6:** not supported. `LpCoreWakeupSource` only has `HpCpu`, and esp-lp-hal's halt just loops. `lp-tempsense` needs its own LP-timer wake and halt, written against the PAC the way ESP-IDF's `ulp_lp_core` does it.

On the C6, the LP program owns all 16 KB of LP SRAM, which is also where esp-hal puts the HP core's `#[ram(rtc_fast)]` data. When `lp-tempsense` runs, its linker script reserves the `lp-shared` block at a fixed address, and the HP core keeps its retained state there instead of in `#[ram(rtc_fast)]` variables.

## Build & commands

The root `.cargo/config.toml` sets no build target and defines `xtask = "run -p xtask --"`. As a result, a plain `cargo test` or `cargo clippy` runs on the host and only covers `default-members` (the `crates/*` libraries and `xtask`). Firmware members are built only through the xtask:

1. It resolves node → sources + board → chip/radio → target, toolchain and features. It validates the board's pins and the node, then exports both the pins and the node parameters.
2. Later: it builds `lp-tempsense` first when a deep-sleep C6/S3 node has the `ds18b20` source, because the HP crate embeds that ELF.
3. For S3 it adds `+esp` and `-Zbuild-std=core`. Add `alloc` there if a node ever needs `esp-alloc`.
4. It always builds `--release` (opt-level `"s"`). Unoptimised esp-hal code breaks bit-banged 1-Wire timing and the LP-core size budget.
5. For `run`, it flashes and monitors with espflash. Later it publishes `schemas.json` first (see [Decoding & Home Assistant](#decoding--home-assistant)).

The firmware gets the values of the node and its board as env vars. `firmware/node/src/config.rs` reads them at compile time into consts: required ones with `env!`, optional ones with `option_env!`. Cargo rebuilds by itself when one changes. A hand-typed `cargo build` doesn't set them, so build the firmware only with the xtask.

- `AIO_NODE_ID`, `AIO_HEARTBEAT`, `AIO_MIN_INTERVAL`: from the node in `nodes.toml`.
- `AIO_PIN_<GROUP>_<NAME>`: one per pin of the node's board, e.g. `lora.sck = 20` becomes `AIO_PIN_LORA_SCK=20`. Pins the board doesn't have (like `busy` on an SX127x board) aren't exported.
- `AIO_TCXO_MV`: only when the board sets `tcxo_mv`.

Never run `cargo build --workspace` or `cargo clippy --workspace`, because the firmware members don't compile for the host. To try a source on a dev board, add the board to `boards.toml` and a node using it to `nodes.toml`.

`.vscode/settings.json` makes rust-analyzer check the firmware like `cargo xtask build dev-c6`: the RISC-V target, dev-c6's chip, radio and source features (plus the other sources), and the `AIO_*` values that the xtask exports for it. When the firmware reads a new `AIO_*` variable or gets a new feature, add it there too. rust-analyzer uses one target for the whole workspace, so the xtask shows false errors in the editor. Comment out `cargo.target` while you work on the xtask.

```sh
# host-side libraries
cargo test                                     # all host tests
cargo test -p eder flags                       # single crate / test-name substring
cargo clippy --all-targets
cargo fmt

# firmware (<node> = entry name in nodes.toml)
cargo xtask help                               # list the commands
cargo xtask check                              # load, print and validate boards.toml and nodes.toml
cargo xtask build   <node>
cargo xtask build   --all                      # every node in nodes.toml, like CI
cargo xtask run     <node> [--port COM5]       # build + flash + monitor
cargo xtask monitor <node> [--port COM5]       # reattach monitor (needs the ELF for defmt)
cargo xtask clippy  <node>

# receiver side (not built yet)
cargo xtask schemas                            # regenerate schemas.json from crates/proto
cargo xtask schemas --publish                  # ... and publish it retained to MQTT (needs AIO_MQTT_URL)
```

CI (`.github/workflows/ci.yml`) runs on every push to `main` and on every pull request, in two jobs. **host** runs `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, and a RISC-V build of the `no_std` libraries. **firmware** runs `cargo xtask check` and `cargo xtask build --all`; it installs the `esp` toolchain for the S3 nodes.

Logging uses `defmt` through `esp-println`, with espflash decoding it via `--log-format defmt`. Panics go through `esp-backtrace`.

## LoRa protocol

Raw LoRa (not LoRaWAN), one-way, no ACKs or retries.

### Radio

- **Shared settings:** 868.0 MHz, SF7, BW 125 kHz, CR 4/5, preamble 8, explicit header, CRC on, normal IQ, private sync word (SX127x 0x12 is equivalent to SX126x 0x1424). These match OpenMQTTGateway's LoRa defaults, so change them only together with the gateway.
- **TX power:** 14 dBm on both radio families. The 868.0–868.6 MHz band allows 25 mW ERP, which the legacy SX127x setting of 17 dBm exceeds with any normal antenna.
- **SX127x:** PA_BOOST. **SX126x:** DIO2 as RF switch, TCXO on DIO3, LDO regulator. The TCXO voltage is a board setting, `tcxo_mv` in `boards.toml`; boards without a TCXO leave it out. The t3s3 uses 1800, like Meshtastic. The legacy code used 3.3 V, which is the fallback if the radio doesn't start at 1.8 V.
- **Driver:** use `lora-phy`, which covers both families; create it with `public_network = false`. It learns that a packet has been sent from the radio's IRQ line (DIO0 on SX127x, DIO1 on SX126x), whose pin `boards.toml` gives as `irq`.
  - **SX126x boards must wire it.**
  - **SX127x boards may leave it out,** like the C6 dev board, whose DIO pins aren't connected. The firmware then gives `lora-phy` a software stand-in for the pin. It reads the radio's IRQ flags register (0x12) over SPI every 1 ms and reports the pin as high once a flag is set, like the legacy drivers did. `lora-phy` masks every flag except the one it waits for, so this matches what DIO0 would do. The stand-in shares the SPI device with `lora-phy` through an `embassy-sync` mutex. It costs about one SPI read per ms while a packet is on air, and no airtime.
  - **The stand-in must wait for the flag itself.** Telling `lora-phy` "check now" every few ms looks simpler but has a bug: `lora-phy` reads the flags and then clears all of them, so a "TX done" that lands between the two SPI steps is lost, and `lora-phy` waits forever.
  - New board designs should still wire the IRQ line; it's one trace and saves the polling.
- **SPI:** 8 MHz, which both families handle.
- **Start-up check:** after `lora-phy` has set the radio up, the firmware reads back the sync word. Anything other than the private sync word means the radio doesn't answer, usually because of a wrong SPI or CS pin. Start-up also has a timeout of 2 s, because a wrong BUSY pin makes `lora-phy` wait forever on an SX126x. Either way the node logs an error instead of `radio ready`.
- **Send timeout:** every send has a timeout of about 2 s. A radio that never reports "done" makes the node log an error instead of hanging.
- **Airtime budget:** at these settings, each packet costs about 21 ms of fixed overhead plus about 1.5 ms per payload byte. The 868.0–868.6 MHz band has a 1 % duty-cycle limit.

### Packet

```
[node_id: u8] { [kind: u8] [section body] }+
```

- **`node_id`** comes from `nodes.toml`.
- **One section per source of the node,** so the packet always holds the node's complete dataset. There are no partial or delta messages and no splitting across packets, so any single received packet is self-sufficient.
- **`kind`** selects the section's schema. Each source has exactly one kind. An incompatible change gets a new kind number (the old kind is never reused); there is no separate version field. For now each kind appears at most once per packet.
- **Section length:** the kind's schema fixes it. A repeated group has no count field, so its section must be last, and a node can have at most one. The firmware emits the sections in a fixed order with the repeated group last.
- **Why a kind byte per section:** one layout ID per node would save 1 byte per extra source. But a packet would then decode silently wrong whenever the receiver's node config is out of date, and kind numbers would have to be generated from config.
- **Body encoding:**
  - Little-endian, with no padding and no floats.
  - No count/length fields when the packet length already implies them.
  - Fixed-point integers in the smallest type that covers the documented physical range.
  - Mark a missing or stale value with a sentinel: `MIN` for signed types, `MAX` for unsigned. Never use 0 for "missing".
- **Send policy, the same for every node.** It lives in `crates/policy`, so the coprocessor can run it too.
  - Send when any field of any source differs from its last sent value by more than its threshold, but never more often than `min_interval`. A change during `min_interval` waits until it ends and is sent then if it still exceeds the threshold.
  - A `ds18b20` sensor appearing or disappearing counts as a change.
  - Otherwise send a heartbeat every `heartbeat`.
  - Thresholds are in the field's wire units. "More than" makes 0 mean "any change", the default for flags and enums. Each numeric field's schema in `crates/proto` gives a default threshold, so unconfigured fields don't send on every last-digit change.
  - `nodes.toml` holds `heartbeat` and `min_interval`, and can override any threshold.
- **Tests:** every kind has golden-byte tests in `crates/proto`, and at least one test covers a multi-section packet.

A single-source node sends `[node_id][kind][body]`. Example sizes: eder 38 bytes, pyromat 30, temp-station with 6 sensors 28 (`battery` + `ds18b20`), eder plus 4 DS18B20 on one node 55.

### Kinds (proposed; confirm the field types with the user before fixing them)

| kind | source | body |
|---|---|---|
| 1 | ds18b20 | repeated `{sensor_id: u16, temp: i16 (1/16 °C, the sensor's raw reading)}`; a repeated group, so always the last section |
| 2 | eder | 36 bytes: flags (masked to the known bits, so never 0xFF), refillMode, degassingStatus, level %, refillMin/MaxThreshold % as `u8`; pressure, targetPressureMin/Max (bar×100), rpmPump1 (%×100), temperature (°C×10), pressureBottom1/Top1 (mbar), tempMulticontrolPcb (°C×100), refillRest (l) as `i16`, signed like the telegram; pump1Seconds, refillTotal (l), degassingSeconds as `u32` |
| 3 | pyromat | tempSystem, tempReturn, tempBufferTop/Middle/Bottom, tempExhaust, targetSystemTemp as `i16` (0.1 °C); restO2, targetRestO2 as `i16`; ventilatorRpm `u16`; airInletPrimary/Secondary, valveReturnMixing, valveBuffer as `u16` (narrow to `u8` once their ranges are verified). The boiler clock fields are dropped, because the receiver timestamps packets |
| 4 | battery | `u8` = (mV − 2000) / 10 (0xFF = not measured) |

For `ds18b20`, `sensor_id` is bits 48..63 of the DS18B20 ROM code, the same IDs the legacy packets used. That way, existing Node-RED sensor-name mappings carry over. Sensors without a valid reading are left out.

**Open:** genuine Maxim sensors have ROM codes `28-tt-tt-ss-ss-00-00-crc`, so these bits are `00` plus the CRC, and two sensors on one node can collide (about 6 % with 6 sensors, 23 % with 12). Decide between keeping these IDs and deriving them from the serial number.

### Decoding & Home Assistant

The flow is: OpenMQTTGateway → MQTT → Node-RED → Home Assistant.

`crates/proto` is the schema registry. Each kind describes its fields: key, type, scale, unit, HA `device_class`/`state_class`, plus an optional trailing repeated group (keyed by `sensor_id` for `ds18b20`). `cargo xtask schemas` exports this to `schemas.json`, together with each node's name, heartbeat and source list, the HA device mapping and `reserved_node_ids` from `nodes.toml`.

**The schema reaches the decoder automatically.**

- **Published on every flash:** `cargo xtask run` publishes `schemas.json` as a retained MQTT message on `aio/schemas` *before* flashing, so the node's first packet already finds its schema.
- **Safe to publish early:** kind numbers are never reused, so publishing a schema whose flash later fails is harmless.
- **Broker address:** it comes from the `AIO_MQTT_URL` env var (e.g. `mqtt://user:pass@host:1883`), which is never committed. If it's unset or the broker can't be reached, the xtask warns and carries on. Run `cargo xtask schemas --publish` later to catch up.

The decoder in `decoder/` is a generic interpreter of `schemas.json`, loaded from the retained `aio/schemas` topic. It has no per-kind code, so adding a node, a source or a field never needs a manual decoder change. It walks the sections in order. If a kind is unknown or the total length doesn't match exactly, it drops the whole packet and logs a warning. For each received packet it:

- **Publishes the state:** one JSON message per node, holding every decoded field of every section, with sentinels turned into `null`.
- **Warns on config drift:** if the packet's kinds differ from the node's source list in `schemas.json`, it logs a warning and still publishes the decoded fields.
- **Publishes discovery when needed:** one retained HA device-discovery message per HA device (HA ≥ 2024.11).
  - **Default device:** `homeassistant/device/aio_<node_id>/config`, holding every source of that node that isn't listed in a `[devices.*]` entry. A node whose sources are all listed elsewhere has no default device.
  - **Declared device:** `homeassistant/device/aio_<key>/config` for each `[devices.<key>]` entry. It may hold sources from several nodes.
  - **Components:** each field is a component with its own `state_topic` (its node's state message), `value_template`, unit, `device_class` and `state_class`. Its `expire_after` is about 2.5 × its node's heartbeat, so a dead node shows as unavailable.
  - **Entity IDs:** `unique_id` is `aio_<node_id>_<source>_<field>`, or `aio_<node_id>_ds18b20_<sensor_id>`. It never contains the device key, so moving a source to another device keeps its entity history.
  - It is republished when HA posts `online` on `homeassistant/status` and when a new repeated-group key appears, for example a new `ds18b20` `sensor_id`.

Unknown node IDs with known kinds still get a default device automatically. A later native HA integration should consume the same `schemas.json`.

**Migration:** OpenMQTTGateway publishes every packet on one topic. Until all legacy nodes are reflashed, Node-RED routes packets whose first byte is in `reserved_node_ids` to the legacy flow and everything else to this decoder, so neither flow sees the other's packets.

HA devices are created by the decoder, not taken from the packet layout, so the radio side never needs to know about them. One complete packet per node becomes one state message, which the decoder maps onto one or more HA devices. Sending one packet per device would only add about 21 ms of LoRa overhead per extra packet, plus partial updates.
