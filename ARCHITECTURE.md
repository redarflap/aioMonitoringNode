# Architecture

Built so far: the scaffold (workspace, xtask, firmware on C6 and S3, LoRa radio, report task, one stub per source, CI). The report task sends the test bytes `[node_id, 0xAA, 0x55]` every `heartbeat`. Everything else here is the target design, built in the order of `plan.md`. Update this file wherever the real code ends up different.

## Concepts

- **Source:** one thing a node reads: `ds18b20`, `battery`, `eder`, `pyromat`. It has a kind number and schema in `crates/proto`, a parser crate if needed, and one firmware module.
- **Node:** one ESP32 with one radio, identified by `node_id`. It runs one or more sources and sends one packet with all their data.
- **HA device:** exists only on the receiver side. By default one per node; `nodes.toml` can regroup sources, even across nodes.

## Repo layout

One Cargo workspace, split by source, not by device. esp-hal and `src/board/` absorb the chip differences.

```
crates/            host-testable no_std libraries, no esp-hal
  proto/           packet format + schema registry (single source of truth for decoders)
  policy/          send policy; also runs on the coprocessor
  eder/            Eder UART telegram parser
  pyromat/         Pyromat CAN frames -> fields
  onewire/         1-Wire + DS18B20 over a minimal bus trait
  lp-shared/       #[repr(C)] HP<->LP shared-memory layout
firmware/
  node/            HP-core firmware: board/, radio/, report.rs, sources/, config.rs
  lp-tempsense/    DS18B20 poller for the C6 LP core / S3 ULP-RISC-V
xtask/             build, config validation, schema export
decoder/           receiver side: Node-RED decode function
boards.toml        board -> chip, radio chip, pins
nodes.toml         node -> board, node_id, power mode, intervals, sources; HA devices
schemas.json       generated by `cargo xtask schemas`; never edit
```

## Design rules

- **Logic in `crates/`, glue in `firmware/`.** Parsing, encoding, send decisions and state machines are pure code with host tests. CI has no hardware tests, so firmware tasks stay too thin to need any.
- **Pins and the radio chip are configuration.** They live only in `boards.toml`, so rewiring or adding a board never touches Rust. The xtask validates them (`xtask/src/validate.rs`) and hands them over as `AIO_PIN_*` env vars and chip/radio features. Only `firmware/node/src/board/` turns pin numbers into drivers; sources get ready-made drivers. Chip-specific code goes into `src/board/<chip>.rs`.
- **Per-deployment values come only from `nodes.toml`:** node ID, power mode, sources, intervals, thresholds, calibration, HA devices. The xtask exports them as `AIO_*` env vars, and `src/config.rs` reads them into consts.
- **A node is composed from sources.** One binary, `firmware/node`. Each source is `src/sources/<source>.rs` behind a `source-<source>` feature and runs as an Embassy task. It writes its latest snapshot (a `crates/proto` struct) into an `embassy-sync` cell and signals the report task. The report task owns the radio: send policy, encoding, sending. Don't recreate the legacy `ServiceManager` singleton.
- **Each node has a power mode,** `always-on` or `deep-sleep`.
  - Listening sources (`eder`, `pyromat`) need `always-on`. Pollable ones (`ds18b20`, `battery`) work in both.
  - Deep sleep: wake, sample once, send if the policy says so, sleep again.
  - With `ds18b20`, the coprocessor polls the sensors and runs the policy, so the HP core wakes only to send (and samples `battery` then).
  - Before sleeping, the HP core arms a backup timer of 2 × `heartbeat` in case the coprocessor hangs.
  - Last sent values live in RTC RAM, in the `lp-shared` layout.
- **`onewire`, `lp-shared` and `policy` must also compile for the LP core:** no alloc, no `core::fmt`, no floats, small code.
- **No heap by default;** use `heapless`.
- **Pin the esp-* versions** in the workspace `Cargo.toml`. Deep sleep, LP core, ADC, RMT, TWAI and RTC RAM sit behind esp-hal's `unstable` feature and can break on minor bumps.

### Adding a source

1. A parser crate in `crates/`, if needed.
2. A kind in `crates/proto`: schema with default thresholds, power requirement, golden-byte tests.
3. `firmware/node/src/sources/<source>.rs` behind `source-<source>`.
4. Its pins in `boards.toml` and its parameters in the xtask.

No decoder change and no new binary.

## Node configuration

`nodes.toml` shows the current fields. Planned:

- `sources.<name> = { ... }` takes the source's parameters (e.g. `max_per_bus`, `poll`) and threshold overrides in wire units.
- `[devices.<key>]` with `name` and `sources = ["<node>.<source>", ...]` groups sources into an HA device, even across nodes. Unlisted sources stay in their node's default device.

## Targets

| | C6 | S3 |
|---|---|---|
| Role | new nodes | existing deployments |
| HP target | `riscv32imac-unknown-none-elf` | `xtensa-esp32s3-none-elf` (`+esp`, build-std) |
| Coprocessor | LP core, `riscv32imac`, LP GPIO 0–7 | ULP-RISC-V, `riscv32imc`, RTC GPIO 0–21 |
| TWAI (CAN) | 2 | 1 |

- Keep S3-only code in `board/`, `#[cfg(feature = "esp32s3")]` blocks, the xtask's `Chip::cargo` and the spots marked "S3 only", so it can be deleted later.
- `ds18b20` polls from the HP core on always-on nodes, and from `lp-tempsense` on deep-sleep nodes (LP/RTC-capable pins only).
- Between polls, the coprocessor must halt and be restarted by its own timer. S3: esp-hal supports this. C6: esp-hal doesn't (as of October 2026), so `lp-tempsense` needs its own LP-timer wake and halt via the PAC, like ESP-IDF's `ulp_lp_core`.
- C6: the LP program owns all 16 KB of LP SRAM, where esp-hal also puts `#[ram(rtc_fast)]`. So `lp-tempsense`'s linker script reserves the `lp-shared` block at a fixed address, and the HP core keeps its retained state there.

## Build & commands

```sh
# host libraries
cargo test                                     # all host tests
cargo test -p eder flags                       # one crate / test-name filter
cargo clippy --all-targets
cargo fmt

# firmware (<node> = entry in nodes.toml)
cargo xtask help
cargo xtask check                              # validate boards.toml and nodes.toml
cargo xtask build   <node> | --all
cargo xtask run     <node> [--port COM5]       # build + flash + monitor
cargo xtask monitor <node> [--port COM5]
cargo xtask clippy  <node>

# receiver side (not built yet)
cargo xtask schemas [--publish]                # regenerate schemas.json [and publish it to MQTT]
```

- Plain `cargo` runs on the host and covers only `crates/*` and `xtask`. Never use `--workspace`.
- Build firmware only through the xtask. It sets target, toolchain, features and `AIO_*` vars, and always builds `--release` (unoptimised code breaks 1-Wire timing and the LP size budget).
- `.vscode/settings.json` mirrors `cargo xtask build dev-c6` for rust-analyzer. Add new `AIO_*` vars and features there too. Comment out `cargo.target` while working on the xtask.
- CI runs fmt, clippy (`-D warnings`), the host tests, a RISC-V build of the libraries, `xtask check` and `xtask build --all`.
- Logging: `defmt` via `esp-println`; panics via `esp-backtrace`.

## LoRa protocol

Raw LoRa, one-way, no ACKs or retries.

### Radio

- 868.0 MHz, SF7, BW 125 kHz, CR 4/5, preamble 8, explicit header, CRC on, private sync word (0x12 on SX127x = 0x1424 on SX126x). These match OpenMQTTGateway; change them only together.
- 14 dBm on both families. The band allows 25 mW ERP; the legacy 17 dBm exceeded it.
- SX127x: PA_BOOST. SX126x: DIO2 as RF switch, TCXO on DIO3 (`tcxo_mv` per board; try 3300 if 1800 doesn't start), LDO.
- Driver: `lora-phy` with `public_network = false`, SPI at 8 MHz. SX126x boards must wire `irq`. SX127x boards may leave it out; the firmware then polls the radio's IRQ flags over SPI. New boards should wire it.
- Airtime: about 21 ms per packet plus 1.5 ms per payload byte. The band has a 1 % duty-cycle limit.

### Packet

```
[node_id: u8] { [kind: u8] [section body] }+
```

- One section per source, so every packet holds the node's complete dataset. No partial or delta messages, no splitting.
- `kind` picks the section's schema; one kind per source, at most once per packet. An incompatible change gets a new kind; numbers are never reused, so there's no version field. A kind byte per section (instead of one layout ID per node) means a stale receiver config can't decode a packet silently wrong.
- The schema fixes each section's length. A repeated group has no count field, so it comes last, and a node has at most one.
- Body: little-endian, no padding, no floats, no count or length fields that the packet length already implies. Fixed-point integers in the smallest type covering the physical range. Missing value = `MIN` (signed) / `MAX` (unsigned), never 0.
- Golden-byte tests for every kind, plus at least one multi-section test.

**Send policy** (`crates/policy`, the same for every node):

- Send when any field differs from its last sent value by more than its threshold, but not more often than `min_interval`. A change during `min_interval` is sent when it ends, if it still exceeds the threshold.
- A `ds18b20` sensor appearing or disappearing counts as a change.
- Otherwise send every `heartbeat`.
- Thresholds are in wire units; 0 means "any change" (the default for flags and enums). Each numeric field has a default threshold in `crates/proto`, which `nodes.toml` can override.

### Kinds (proposed; confirm the field types before fixing them)

| kind | source | body |
|---|---|---|
| 1 | ds18b20 | repeated `{sensor_id: u16, temp: i16 (raw 1/16 °C)}`, always last. `sensor_id` = bits 48..63 of the ROM code, like the legacy packets. Sensors without a valid reading are left out |
| 2 | eder | 36 bytes: flags (masked to the known bits, so never 0xFF), refillMode, degassingStatus, level %, refillMin/MaxThreshold % as `u8`; pressure, targetPressureMin/Max (bar×100), rpmPump1 (%×100), temperature (°C×10), pressureBottom1/Top1 (mbar), tempMulticontrolPcb (°C×100), refillRest (l) as `i16`; pump1Seconds, refillTotal (l), degassingSeconds as `u32` |
| 3 | pyromat | tempSystem, tempReturn, tempBufferTop/Middle/Bottom, tempExhaust, targetSystemTemp as `i16` (0.1 °C); restO2, targetRestO2 as `i16`; ventilatorRpm, airInletPrimary/Secondary, valveReturnMixing, valveBuffer as `u16` (the last four may narrow to `u8`). No boiler clock: the receiver timestamps packets |
| 4 | battery | `u8` = (mV − 2000) / 10, 0xFF = not measured |

### Decoding & Home Assistant

Flow: OpenMQTTGateway → MQTT → Node-RED → HA.

- **Schemas:** `crates/proto` describes each kind's fields (key, type, scale, unit, HA `device_class`/`state_class`, optional trailing repeated group). `cargo xtask schemas` exports this to `schemas.json`, with the nodes (name, heartbeat, sources), HA devices and `reserved_node_ids`.
- **Publishing:** `cargo xtask run` publishes `schemas.json` retained on `aio/schemas` before flashing. The broker comes from `AIO_MQTT_URL` (never committed); if it's unreachable, the xtask warns and carries on.
- **Decoder:** `decoder/` interprets `schemas.json` generically, with no per-kind code. Unknown kind or wrong total length: drop the packet and warn. Kinds that differ from the node's source list: warn, still publish. Each packet becomes one state JSON per node, with sentinels as `null`.
- **Discovery** (HA ≥ 2024.11), retained, one message per device: `homeassistant/device/aio_<node_id>/config` for a node's default device (its sources not listed in any `[devices.*]`), `homeassistant/device/aio_<key>/config` for declared devices. Each field is a component with its node's state topic and `expire_after` ≈ 2.5 × heartbeat. `unique_id` = `aio_<node_id>_<source>_<field>` or `aio_<node_id>_ds18b20_<sensor_id>`, never the device key, so moving a source keeps its history. Republished on HA `online` and when a new repeated-group key appears. Unknown node IDs with known kinds still get a default device.
- **Migration:** Node-RED routes packets whose first byte is in `reserved_node_ids` to the legacy flow, all others to this decoder.
